# Per-engagement SQLite Store (`scan.db`)

> Part of the MonkeyX Core docs. See [`../CLAUDE.md`](../CLAUDE.md) for the index.

## Per-engagement SQLite store (`scan.db`)

Each engagement gets a `scan.db` at the **output-dir root** (next to
`discovery-ledger.jsonl`), created and written by the engine — `core/scan_db.py`.
It is the emerging **source of truth for new consumers** (report renderers, API),
while the engine keeps **dual-writing** the legacy JSONL/JSON so existing readers
are unaffected. Every DB write is wrapped so a failure logs a warning and never
aborts a scan; the JSONL remains the fallback.

**Connection model:** one long-lived WAL connection per engagement (`ScanDB`),
guarded by a single lock so it is safe to share across parallel-group worker
threads. Uses WAL, `synchronous=NORMAL`, `foreign_keys=ON`, and `busy_timeout`.
Schema setup is idempotent (`CREATE TABLE IF NOT EXISTS` + a guarded `ALTER TABLE
ADD COLUMN` migration list), so `--continue`/`--resume` reopen the same file and
upsert. This is engine-owned per-run state (mirrors how `~/.monkeyx/knowledge.db`
is engine-owned). `.gitignore` already covers `*.db`/`-wal`/`-shm`.

**Close checkpoints the WAL.** `ScanDB.close()` runs `PRAGMA
wal_checkpoint(TRUNCATE)` before closing, so `scan.db` is self-contained on disk
— a downstream consumer that archives the output-dir root into a results zip can
open `scan.db` from the zip *without* the `-wal`/`-shm` sidecars. `run_modules`'
`finally` calls
`ledger.close()` + `tracker.close()` on every exit path (normal, exception, and
the `sys.exit` pause/cancel), and `normalize`/`ai_validate` close their own
short-lived handles. **If you add a new writer, close it** or its committed rows
may be stranded in the WAL when the run is zipped.

**Tables:** `findings`, `validations`, `targets`, `target_parents`, `ports`, `exclusions`,
`web_endpoints`, `web_dirs`, `mx_domains`, `progress_events`, `module_runs`,
`module_coverage`, `meta`.

`web_dirs` holds discovered web content — directory/file brute-force hits
(ffuf/feroxbuster) AND crawled URLs (katana/gau) — as `dir_hit` records, minted
by `normalize._mint_web_dirs` and deduped on `(url, tool)`. It backs the
webserver's **Web Directories** view. Kept separate from `findings` — dir hits
are recon leads, not vulnerabilities (`ai_analyze` still promotes notable ones
into attack_chains). ffuf is parsed from its JSONL; feroxbuster from its text
output (status/size via regex); katana/gau are one-URL-per-line files, and
`normalize._parse_crawled_urls` mints only URLs with a path/query (bare site
roots are endpoints, not content, and stay out).

`targets` carries the scope verdict in **two** columns: `in_scope` (INTEGER 0/1 —
the authorization boolean) and `scope` (TEXT — the classification/reason:
`explicit` user-provided, `derived` discovered, `excluded`). Both are the
*result* of the ledger's parent-chain fixpoint (re-asserted by
`sync_scope_to_db()` at end of load + end of run), not an in-progress guess.
`upsert_target` last-writes `in_scope` but COALESCEs `scope` (never nulled).
Query in-scope targets with `WHERE in_scope=1`.

`meta` holds engagement identity (see "Engagement identity" below):
`engagement_uuid` (stable, first-wins), `created_at`, `output_prefix`,
`schema_version`, `progress_run_seq`, plus two resume markers:
`ledger_authoritative` (`"1"` once a run has persisted fixpoint-resolved ledger
state — gates DB-sourced resume via `load_from_db`; absent = the DB predates the
migration, so `RunPredatesDbMigration` is raised and the operator must start
fresh) and `clean_shutdown` (`"1"` only after a graceful end synced scope;
absent/`"0"` = crash/in-progress, so the next resume re-runs the scope fixpoint
rather than trusting the persisted `in_scope` flags).

### Engagement identity (`meta.engagement_uuid`)

Every scan.db stamps a stable `engagement_uuid` on first open
(`ScanDB.stamp_identity`, via `TargetLedger.stamp_identity` from `run_modules`).
First-wins: preserved across `--continue`/`--resume` even though the API mints a
new per-run id each invocation, so all runs of one engagement share it — the key
a future cross-project rollup joins on. Generated by the engine if not supplied;
the `--engagement-id` CLI flag lets the API inject its `run_id` (the API's
command builder would append `--engagement-id <run_id>`; not yet wired in dev).

### Module coverage (`module_coverage`)

Tracks **what each module was fed and the outcome** — the answer to "what did
module Y scan?" and "what touched host Z?", with `run_seq` history so a
`--continue` re-run appends rather than overwrites. Columns: `(id, module,
target, target_type, run_seq, step_index, status, ts)`, indexed on `target` and
`(module, run_seq)`.

**status lifecycle** (honest by design — never claims a scan happened when it
can't prove it):
- `fed` — target was submitted to the module (recorded from the same post-scope-
  gate input files the forensic snapshot copies, BEFORE the module runs). Also
  the terminal state for tools with no reach-extractor (never guessed).
- `reached` — target appears in the module's output (proof of reach).
- `no_response` — fed, module finished, target absent from output = the
  **actionable "maybe missed" bucket** (down, blocked, or truly missed — flagged
  for a human, asserted as neither). This is what the webserver's coverage badge
  counts.
- `step_failed` — the module run itself errored.

Written by `TargetLedger.record_coverage` (batched, best-effort) at both the
sequential and parallel-group step sites; reconciled by
`TargetLedger.reconcile_coverage` → `ScanDB.reconcile_coverage` right after each
module, scoped to `(module, run_seq, step_index)` and only touching `fed` rows
(idempotent). Per-tool reach extraction (`workflows._reached_hosts_from_output`)
currently covers **nuclei, httpx, nmap** (field choices match normalize's
parsers); `_coverage_host_key` normalizes the fed-URL vs output-bare-host
mismatch. Adding a tool = one extractor branch. **This is fed-vs-reached
tracking, not proof of a completed scan; a down host and a blocked host both land
in `no_response` — a physics limit of external scanning, not a bug.**

### Shared finding ID

`scan_db.finding_id(host, port, proto, claim)` = first 12 hex of
`sha1("{host}|{port}|{proto}|{claim}")`, with `host` normalized (lowercased,
trailing dot stripped — identical to `eval_harness._norm_host`). `claim` is the
tool discriminator that, with host/port/proto, uniquely identifies a finding:

| tool | claim | source field |
|------|-------|--------------|
| nuclei | template id | `template_id` |
| nmap script | script id | `method` |
| bbot | event type | `bbot_type` |
| dns_security | check slug | parsed from the `[check]` prefix in the title |

`modules/normalize.py:_claim_for()` derives it at mint time; `ai_validate`
recomputes the same id from the same raw record to join a verdict back exactly.

### Who writes what

- **`normalize`** mints a `findings` row per findings-type record
  (`nuclei_finding`, nmap `script_output`/`vulnerability`, bbot
  `finding`/`vulnerability`, `dns_security`) *after* the normalized JSONL is
  written (JSONL stays byte-identical). Open ports / subdomains / dir hits are
  **not** findings — ports live in the `ports` table via the ledger. Upserts
  never clobber triage columns, so a `--continue` re-normalize can't wipe a
  recorded verdict.
  - **NSE script classification is state-aware** (`_classify_nse_script`):
    a vuln-library script whose `<elem key="state">` says the host is affected
    (`VULNERABLE`/`EXPLOITABLE` → `type=vulnerability` sev `medium`; `LIKELY
    VULNERABLE` → `low`) becomes a real finding; pure-info scripts (ssl-cert,
    http-title, service banners) and vuln scripts that reported `NOT VULNERABLE`
    stay `script_output`/`info`. Both are still minted into `findings` (as
    queryable context), but only genuine findings pass `scan_db.is_finding_record`
    — the filter report/CSV/summary/AI-context use so info context (thousands of
    ssl-cert rows) doesn't drown the real findings. `REAL_FINDING_TYPES` (excludes
    `script_output`) vs `FINDING_TYPES` (what gets minted) is the distinction.
- **`TargetLedger`** dual-writes `targets`/`ports`/`mx_domains` from its existing
  write funnel (`_write_entry`/`_write_entry_unlocked`) under the same lock. Scope
  resolution stays in memory (the parent-chain fixpoint is more than a parent
  walk); the ledger persists the **result**. `sync_scope_to_db()` re-asserts the
  fixpoint-resolved `in_scope` flags at the end of `load_from_disk` and at the end
  of a live run (so a child logged before its parent gets the corrected flag).
- **`ProgressTracker`** mirrors every event into `progress_events` and bumps
  `module_runs` (cumulative count + latest status by timestamp) on
  step_completed/step_failed.
- **`ai_validate`** records a `validations` row per result and writes the verdict
  to **two** places: `ports.verdict` (via `set_port_verdict`, keyed on
  host/port/proto) and `findings.verdict` on each exactly-joined finding.
  ai_validate assesses ai_analyze *recommendations*, which are **port/service
  scoped** ("Test Exchange SMTP on host:587"), not per-finding — so the port is
  the verdict's natural home and always receives it (validations carry a `proto`,
  default `tcp`, for the ports join). The finding-level join (`_match_finding_ids`)
  additionally recomputes the `finding_id` from raw evidence, keyed on the
  `[template-id]`/CVE token the recommendation carries or an unambiguous single
  finding on that host:port; multi-finding hosts store a `NULL` finding_id (the
  port link still carries the verdict) and are logged. `validated-findings.json`
  gains additive `finding_id`/`finding_ids`/`port_proto` fields.

### Findings triage state

The `findings` table carries operator/agent state beyond the raw evidence:
`verdict` (confirmed/refuted/unclear/error), `triage_status`
(new/triaged/accepted_risk/remediated), `false_positive` (0/1), `notes`. Only
`verdict` is written today (by `ai_validate`); the rest are the surface for a
future triage UI/API. Re-ingest via `--continue` never overwrites them.

### Severity re-rating

`severity` is the **effective** (elevated) rating everything sorts by, not
necessarily the tool's own. `upsert_finding` runs `core/severity_rerate.rerate`
(elevate-only, curated allowlist) at mint time and centralizes it so every
finding writer (normalize, ai_analyze_gowitness, …) is consistent. The change is
auditable: the tool's original rating is preserved in `original_severity`, with
`severity_source` and `rerate_reason` recording what elevated it.

### Evaluation harness

Because validations now carry a `claim`, `core/eval_harness.py` scores on
`(host, port, claim)` when the produced run has a claim for that triple, falling
back to `(host, port)` otherwise. This distinguishes two findings on one
host:port with opposite verdicts, which the host:port-only key silently merged.
